## note_configuration — Requirement Subtype Schema (seeded from knowledge_partner/requirements)

**Date:** 2026-09-02
**Provenance:** carried forward directly from `requirements`/note-0001 in `knowledge_partner` — the same schema, unchanged, not a new format invented for this repo.

**Schema fields:**
- **Requirement ID** — a stable, unique identifier for the requirement.
- **Statement** — the requirement itself, stated as a single testable sentence.
- **Rationale** — why this requirement exists; the reasoning behind it, not just the requirement text.
- **Source** — where this requirement came from (stakeholder, standard, prior lesson learned, etc.).
- **Priority** — relative importance, for trade-off decisions.
- **Constraint flag** — explicitly distinguishes a constraint (a boundary condition) from a functional requirement, since the two are verified differently.
- **Verification method** — how satisfaction of this requirement will actually be checked (inspection, analysis, demonstration, test).
- **Status** — current lifecycle state (draft, reviewed, approved, verified, etc.).

**Reference:** `requirements`/note-0001, note-0002 in `knowledge_partner` (the original schema and its founding scope statement), `candidate_playbooks`/OBS-0016 in `knowledge_partner` (the playbook candidate this repo is the real, live test case for).
